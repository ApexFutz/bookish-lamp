# ADR-0001: Technology stack & architecture

- Status: Accepted (MVP) — to be confirmed by a thin vertical-slice prototype before full build
- Date: 2026-08-07

## Context

This is a warehouse skills-matrix + access-control application: users have a job-function role (baseline permissions) plus certified equipment qualifications (for example, forklift) that layer on extra permissions, governed by authorization tiers. It is being built for a small company with no in-house software development department, to be handed off and client-owned.

The overriding priorities are, in order:

1. Low maintenance — it must keep working with minimal ongoing development effort.
2. Safety — wrong authorization can get someone hurt; correctness and reliability first.
3. Consistency — it must reliably perform its implied actions (expire certs, deny the unqualified, alert authority).
4. Mobile + desktop — bonus: higher tiers can monitor from phones (limited functionality).
5. Professional, dynamic UI.

## Decision

Use a boring, batteries-included, server-rendered monolith delivered as one responsive Progressive Web App (PWA): a single codebase serving phone, tablet, and desktop, with no native apps and no separate SPA frontend.

- Framework: Django (Python)
  - Built-in admin auto-generates most CRUD for users, roles, tiers, qualifications, and audit-related management.
  - Built-in auth + permissions provide a strong baseline and reduce operational risk.
  - LTS / low-churn release cadence and a large contractor pool make future maintenance easier.
  - Rails 8 is acceptable as an equivalent, but Django was chosen for the client’s handoff and maintenance profile.
- UI: server-rendered templates + HTMX + Alpine.js + Tailwind CSS
  - Dynamic and polished without a SPA build pipeline.
  - Tailwind is mobile-first and naturally responsive.
- Mobile delivery: PWA
  - Installable, browser-based, and usable across desktop and mobile.
  - No app store burden or separate native codebase.
- Database: PostgreSQL
  - Managed PostgreSQL is recommended for production.
  - DB-level constraints enforce invariants and protect safety-critical rules.
- Authentication: Django built-in auth, not a third-party JavaScript auth library.
- Authorization: in-app tier + qualification model behind a single resolver, computed at read time.
  - No external policy engine such as OpenFGA or Cedar for MVP.
  - This keeps operational complexity low while leaving room to adapt later if needed.
- Background jobs: durable and retryable
  - Used only for notifications and operational follow-up.
  - Never relied on for safety enforcement.
- Hosting: managed PaaS the client owns
  - Render / Railway / Fly.io + managed Postgres with backups.
  - Low-ops, portable, and suitable for a client-owned deployment model.
- Observability: Sentry + uptime monitoring + a heartbeat on the expiry job.
  - A stall should be detected quickly rather than silently ignored.

## Safety architecture (non-negotiable)

Following fail-safe design (Saltzer & Schroeder, 1975):

- Deny-by-default / fail-safe
  - Any check that cannot be confirmed is denied.
- Read-time derivation
  - Validity is derived from the expiry date at check time, never trusted to a cron-flipped flag.
- Offline is read-only and clearly marks staleness; never authorizes on stale data.
- Immutable audit log of every grant/revoke
  - Who, what, and when are persisted.
- Database constraints + automated tests
  - These guard the authorization logic against regressions.
- Fail loudly
  - Expiring or expired registrations raise prominent alerts and push notifications.

## Consequences

Positive:

- Minimal moving parts and dependency churn → lowest realistic maintenance.
- One codebase covers all devices; the PWA gives mobile monitoring without app-store overhead.
- Django admin + read-time fail-safe authZ align directly with the safety goals.

Negative:

- UI ceiling is slightly below a full React SPA.
- Rich data viz (heatmaps, optional 3D warehouse map) should be built as targeted JavaScript islands rather than a full single-page application.
- iOS PWA has known limitations around storage eviction and some APIs; this is adequate for monitoring, but native device integration would need reevaluation later.

Note: "Low maintenance" does not mean "zero maintenance." A modest support retainer for security patches and break-fix is recommended; unpatched safety software is itself a hazard.

## Alternatives considered

### Next.js / React SPA + Better Auth

Best UI ceiling, but ecosystem churn makes it high-maintenance for a company with no developer team. Rejected.

### Native iOS / Android apps

Worst fit for low maintenance due to multiple codebases and app-store lifecycle overhead. Rejected in favor of PWA.

### External authorization engine (OpenFGA / Cedar)

Powerful but adds another service to operate. Rejected for MVP; the read-time resolver is kept behind an interface so it could be replaced later.

### Buy vs build (COTS skills matrix such as AG5 / Kahuna / Signalo)

Genuinely the lowest-maintenance option, but build was selected for control, workflow fit, and cost-per-seat reasons.

## Licensing and cost implications

- Django is open-source under the BSD 3-Clause license and is free to use.
- PostgreSQL is open-source under the PostgreSQL License and is free to self-host or run under managed hosting.
- Tailwind CSS is open-source under the MIT license and is free to use.
- HTMX and Alpine.js are open-source and cost-free to use.
- Production hosting costs are typically modest if deployed on a managed PaaS with a managed database.
- Client-side operational costs are mainly hosting, backups, uptime monitoring, and occasional security patching or support retainers.
- The platform is intended to be self-hostable and client-owned without locking the client into a proprietary SaaS dependency.

## Implementation note

The short-term prototype should prove the stack with a thin vertical slice:

- log in
- view qualifications
- an admin grants a qualification such as forklift
- the user’s effective permissions update immediately through read-time calculation
- the change appears in the skills matrix

This validates the architecture before the full build.

## Decision locked

Decision locked (2026-08-07): Django (Python).

Rails 8 was the close alternative, but for a client with no in-house developer team that must be handed off, the deciding factors are the larger and cheaper Python contractor hiring pool and Django’s built-in admin, which covers much of the users, roles, tiers, qualifications, and audit CRUD for free. This supersedes any earlier note suggesting Rails 8 was an acceptable equivalent. The decision would only be revisited if the long-term maintainer is a Ruby developer.
